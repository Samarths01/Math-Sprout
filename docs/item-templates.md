# Item templates

Templates are data. A server interpreter draws operands, computes the answer, and stores an `item_instances` row. The client never generates a problem and never sends an answer key.

Progression in this release is `rules-v0`. Each skill is assigned step 1 (Warm-up). Issuance reads that assignment and does not write it, and it does not write learner state. Issuance stays on the requested skill at its assigned step, picks the least-recently-seen template that still has an unseen item (skipping the template the child was just issued, read from `item_instances.issued_at`), and takes a shuffled unseen item from it. A template that has run out is skipped and is not a switch. If the only template that still has an unseen item is the one just used, issuance switches and records `issue_reason = template_switch`. If that skill has no unseen item, the switch is `exhausted_switch`. Either switch goes to the next skill in the catalog rotation at that skill's assigned step, skipping skills that also cannot draw. A switch counts as normal evidence. The child header changes to that concept name and shows no toast. If no other skill has a fresh item, issuance repeats the same skill and assigned step by inserting a new `item_instance_id` copied from the instance seen longest ago (`exhausted_repeat`). That new row is issued with `evidence_eligible` false. It does not draw a harder step. An attempt on the repeat never counts as evidence. Only the child's first attempt on the original instance does. A retry or a replay of the same instance does not. The child never sees an empty screen. Seen time is `issued_at` on the child's issued instances. There is no separate template counter. Template weight is one knob, `TEMPLATE_DRAW_WEIGHTS`, defaulting to equal weight (`DEFAULT_TEMPLATE_DRAW_WEIGHT`). Equal weight is least-recently-used. Ties break with the seeded shuffle. `issue_reason` is `normal`, `template_switch`, `exhausted_switch`, or `exhausted_repeat`. The rotation gates count both switch reasons toward the 10% skill rate and the one-switch session cap. Distinct templates are the templates the child was actually issued in the week. `issue_reason` is `normal`, `exhausted_switch`, or `exhausted_repeat`, and it stays off the child payload. `poolIssuanceCounts`, next to `formatRejectRates`, is the dev readout of issued items, `exhausted_switch`, `exhausted_repeat`, and the switch rate for each skill, step, and template version. It is not on the child or parent payload. The catalog rotation is also checked as one session of 15 items a day for 7 days, and as two sessions of 15 items a day for 7 days (210 items) on that same 11-slot rotation. Those two runs are one child each, with a random child id. Two more runs repeat the week for 20 children with fixed ids, one session a day and two sessions a day, so the template floor is checked across children and not by pinning one seed. On both runs each skill's switch rate, `exhausted_switch` divided by items issued for that skill, stays at most 10%, with zero exact repeats, zero `exhausted_repeat`, and at most one `exhausted_switch` in any 15-item session. That session limit is a rotation-test assertion. Issuance does not enforce it, so a second drained pool in the same session can still switch. The no-back-to-back rule records `template_switch` when the previous template is the only one of the skill that still has a fresh item: the pool is not empty, and the issue is not `normal`. `exhausted_switch` is the empty pool. Both reasons count toward the 10% rate and the session cap. The instance stores `requested_skill_id`, and the switch rate credits that requested skill. Each skill also shows at least 3 distinct templates issued on each of those runs. A non-evidence repeat keeps the last saved band view on screen and in storage. It mints no `MasteryBandTransition`, `BadgeMilestone`, or `ConceptProgressTick`, and it does not record a Stretch step. XP and fuel still follow the normal path, the same way a form mismatch still mints effort without a concept tick. Step-1 `frac-equiv-improper` version 4 caps the whole part of the answer at 3. Its step-1 denominators stay 5 and 6, the same set as version 3, so that step holds 21 items. Versions 2 and 3 stay at 45 items with answers up to `6 5/6`. Wholes of 4, 5, and 6 do not fit step 2's span of 3–4, so they are dropped from step 1. Comparing unit fractions at step 1 is a 19-item pool. A separate stress test still issues 210 items inside each skill's own pool.

Each skill has one legacy `v0` seed (the original fixed item, `provenance: seed`) and at least three generated templates. Legacy rows do not count toward that bar. Finding an equivalent fraction has four generated templates so the written form can be required: lowest terms, improper, or mixed. Other fraction skills compare equal values, so `2/4` matches `1/2`.

A template version is immutable. Changing a spec means adding a new version. `tests/template-version-snapshot.test.ts` hashes each spec and stores the engine pool count for each step next to that hash. A pool-count change at the same version fails that test.

`parent_prior_grade` and `parent_prior_difficulty` are nullable columns on the template version. Every seed leaves them null. Issuance does not read them.

An unreadable answer is not an attempt (Architecture §29). The server writes no attempt row, mints nothing, and returns `format_rejected` with no verdict and no fuel line. The idempotency key is not consumed, so the next readable answer on that issued item scores normally. The item stays in the 7-day no-repeat window because it was already issued. Rejects are logged in `answer_format_rejects` (`item_instance_id`, `template_version`, `provenance`, `answer_kind`, `build_sha`, `policy_version`, `reject_seq`, `rejected_at`) with no raw child text. `reject_seq` starts at 1 for each item instance. Those rows never enter the attempt log, the mastery estimator, the band, or fuel.

`parseAnswer` lives in `lib/answer-parser.ts`, which imports nothing. The client and the offline queue use that same function. The server is the only scorer.

When an item is issued, the child payload carries `answerKind` (`whole` or `fraction`) and `formatExample`. `answerKind` comes from the template family, not from the value of that draw. Every item from a fraction template is `fraction`, including when the answer simplifies to a whole number such as `3/4 + 1/4`. The server picks the example and it is never equal to the canonical answer: whole templates use `3`, or `4` when the answer is 3; fraction templates use `1/2`, or `1/3` when the answer is equivalent to 1/2 (including `2/4`). The client does not compute or receive the answer. Offline-batch items carry the same two fields. The hint copy lives in `FORMAT_HINT_COPY`: `Use numbers only, like {example}.` and `Write it as a fraction, like {example}.` A fraction answer of `1` matches `4/4` by value unless the template sets `require_form`. A `mixed` template never draws an operand set whose canonical answer is a whole number, because the mixed form of `4/4` is just `1`. `improper` still rejects `1`. `lowest_terms` step 1 draws only proper fractions (value below 1); values above 1 are allowed from step 2. Lowest terms accepts a reduced improper fraction, a reduced mixed number (`1 1/2` is correct, `1 2/4` is `form_mismatch`), and whole writings such as `1` and `3/1`. Lock-in shows the stored canonical form. When the value is right and the written form is wrong, the attempt is still a miss and the row stores `form_mismatch`. The child response carries `reason: { kind: 'wrong_form', required }` and the Not-yet copy in `lib/wrong-form-copy.ts`. That try closes the item and mints the same effort XP and qualifying-day progress as a wrong-value miss. `form_mismatch` stays off the child payload. The reason is derived on read from the attempt row and that item's frozen `item_instances` row: the stored answer, the required form captured at issue, and the grade. It does not read the live template. An attempt with no frozen form returns `reason: null`. The reason is not written into `beats_json`. Issuance slots use a per-session counter that only increases. The catalog length rotates skills. A session that already has issued items requires `itemInstanceId`. A missing or invalid id returns `{ error: "invalid_attempt", retryable: false }`. The offline queue drops that entry after one try and warns with the idempotency key only. A live tab reloads the session. Network failures and 5xx stay retryable. The offline batch keeps at most 3 unanswered instances per session (`OUTSTANDING_UNANSWERED_CAP`), counting the item already on screen. A new batch key does not add another instance once that cap is reached. `MIN_PER_TEMPLATE_STEP` is 10 distinct drawable items for each template version at each step, counted by `eligibleDraws` after the lowest-terms proper-only filter and the mixed no-whole filter. `MIN_PER_SKILL_STEP` is 20 across a skill's newest templates at that step. Step 1 is the CI gate. A step 2 or step 3 pool under the floor is pre-PR-B work and does not fail that gate. An allowlisted pool is excused from the size check only. The heavy-week simulation still requires zero `exhausted_repeat` from every pool, allowlisted or not. Wider operand boxes ship as a new version inside the same feature band. Step-1 versions that cannot reach the floor without leaving that band are listed on `TEMPLATE_POOL_GAPS` and `SKILL_POOL_GAPS`. Template versions are inserted on every startup, and a changed `content_hash` for an existing version throws.

Blank answers are unchanged: an `empty_answer` review-lane try mints no XP, is not a celebrate miss, and still occupies a slot in the mastery window.

`UNPARSEABLE_BEHAVIOR` in `lib/unparseable.ts` is the only switch (`'retry' | 'lock'`). It defaults to `'retry'`: the item stays open, the typed text stays in the blank, and one slate hint sits under it. `'lock'` consumes the instance, writes no attempt, and the child line is `That answer stays quiet.` Changing that one constant is the whole decision.
